# 下一阶段顺序（2026-09-17 用户确认）

顺序：当前 UI/交互收口 → 当前 2D 精灵式 RPG 的完整主线与动态中间内容 → 旧文字/电影式 RPG 制作技能正式更新。不并行扩大三个方向；继续现有游戏，不据此创建新 UUID、游戏或改写旧旅程。

## 1. UI 与交互收口

完成移动/摇杆/附近行动反馈、短对白与行动选择、自由输入、加载衔接、随身物品/旅程入口、小屏中英文适配及电影式结局演出。保留满屏放大、跟随镜头及已接受美术方向。

验收一次代表性的“探索→对话→用物品/解谜→切场景→结局→续玩”流程，复验受改动影响的核心状态，不反复走全部路线。检查画面不跳动、按钮清晰、测试功能隔离、手机尺寸不溢出；自动化/视口模拟与真实手机、声音听感证据分开记录。

完成标准：没有妨碍探索的主要交互问题，形成可持续使用的 UI 基线，不以无限视觉精修拖延第二阶段。本地优先，阶段版本合并发布。

## 2. 2D RPG：完整主线与动态中间内容

当前取信即可离开的主线和可选暗房扩展不等于完整动态章节链。先绘制主线依赖与自然地图出入口，说明玩家每段发现、选择、解决的事情及持久后果；主线目标、关键因果和结局条件固定，中间部分内容可以每局不同。章节是探索进度，不是强制舞台式转场。

先验证两个相接的动态探索环节，证明一次完成产生的真实线索/后果能约束下一个生成环节，再按体验扩到约 2–3 个主要动态环节。数量是本游戏实验规模，不是通用技能硬指标。45–60 分钟延续为内容设计目标，未实测前不声称达到；不靠走路、等待和重复对话凑时长。

生成实例需要进入条件、可用实体、行为、完成证据、后续出口和持久 ID，经过准入后才改变游戏事实。优先预备下一环节；空间布局、碰撞、出入口和必需线索齐备才可进入，非关键氛围图可后补。不让玩家在空白无规则场景行动，也不要求全部装饰先生成完。失败恢复不授予完成事实。

同一旅程保存已生成内容与规则版本，刷新不重新生成，旧旅程不追加新门槛。通用运行时能力与服务支持须据代码/API逐项验证，不把现有单一暗房模板或随机预设当成已实现任意动态章节。

验收：两份真实生成且决策/线索关系有差异的旅程；一条最短合法主线及一条代表性探索路线；一次恢复和一次慢/失败生成。分别记录核心机制、实际内容、节奏和未验证体验。模型/媒体调用沿用有效授权，新增调用范围必要时说明具体缺口。

完成标准：能体验完整主线，有真实动态中间内容，结局由足够的已完成因果决定；不能由一件早期道具或模型一句话直接触发。保留合理替代解法与明确提前退出，不把所有支线强制化。

## 3. 旧文字 / 电影式 RPG 制作技能更新

现有技能的问题分析和设计要求可先记录，但本阶段才进行完整模板/规则/验收改造及正式打包。参考 build-stateful-story-game、create-rpg-game 和 create-hosted-rpg 的实际实现，不自动迁移后台。

将第二阶段验证的主线里程碑、动态中间内容准入/恢复、章节与终局区分、最短通关路线检查移植到各自适用的壳。文字式保留开放行动和累积阅读；电影式的字幕页/图片步骤不能作为剧情进度。不是所有 RPG 都要长篇、同样章节数或强制动态生成。

对“Prolog 后太快结局”需检查受影响作品的迁移前后定义和执行轨迹，不能仅凭时间相关性认定规则引擎有错。分别补充制作要求、已有模板能力和服务缺口；不能用提示词代替权威结局条件，不能宣称技能文档更新已经修好线上作品。

验收：文字与电影式各一份代表性产物，确认章节可继续、真正结局条件准确、自由行动没有退化为猜预设口令；动态能力只在实际支持且验证后标为可用。最后更新技能包与验证记录；已分发包和线上旧游戏的升级范围另列，不自动批量发布。

## 推进方式

按阶段自主推进，不逐步索要审美确认。汇报当前阶段、已完成、剩余和实际阻塞。优先验证核心机制；只在缺有效授权、真实平台能力或无法替代的外部条件时请求用户协助。保持现有大目标，技能制作不能先于游戏机制的真实验证。
